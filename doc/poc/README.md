## 1. 目的

予想（勝率・複勝率・着順分布）を出す二つの手法を、同じレース入力と同じ指標で検証する。

| 手法 | 文書 | 概要 |
|------|------|------|
| 既存手法 | [existing-method.md](./existing-method.md) | 能力・スタミナ・ペース・馬同士の相互作用を時間ステップで進め、Monte Carlo で着順分布を得る |
| 提案手法 | [proposed-method.md](./proposed-method.md) | LightGBM の utility、展開シナリオ混合、Plackett-Luce、その分布からの Monte Carlo サンプルで着順分布を得る |

既存手法の検証は、基本設計の Phase 1〜4 に相当するシミュレータが仕様どおりの順位・タイム・展開を出すことを確認する。提案手法の検証は、同じ予想量を統計モデルで出せることと、ペースを混ぜたときに順位分布が想定方向へ動くことを確認する。

基本設計は [基本設計書](../basic-design/basic-design.md) を参照する。

## 2. 共通の入出力

両手法は同じ出走表を読む。フィールド名は基本設計 4 章に合わせる。

```json
{
  "raceId": "poc-001",
  "course": { "surface": "turf", "distance": 1600, "direction": "left" },
  "going": "good",
  "entries": [
    {
      "id": "h1",
      "gate": 1,
      "post": 1,
      "jockey": { "skill": 50 },
      "weight": 55,
      "horse": {
        "id": "h1",
        "speed": 70,
        "stamina": 70,
        "acceleration": 50,
        "cornering": 80,
        "runningStyle": "front",
        "aptitudes": { "turf": 1, "dirt": 1, "bestDistance": 1600 }
      }
    }
  ]
}
```

列挙値は次で固定する。

| 項目 | 値 |
|------|----|
| surface | `turf` / `dirt` |
| direction | `right` / `left` |
| going | `good`（良） / `yielding`（稍重） / `soft`（重） / `heavy`（不良） |
| runningStyle | `front`（逃げ） / `stalk`（先行） / `mid`（差し） / `closer`（追込） |

予想の共通出力は次の 3 つとする。着順は 1 始まりである。

| フィールド | 意味 |
|------------|------|
| `winProb` | 1 着確率 |
| `top3Prob` | 3 着以内確率。出走頭数 n が 3 未満のときは n 着以内 |
| `meanRank` | 平均着順 |

既存手法は、これに加えて 1 回のレース結果（着タイム、着差、通過地点、再生フレーム）を出す。提案手法の PoC は順位分布を出し、タイムとフレームは出さない。

## 3. 共通データ

| データ | 生成 | 用途 |
|--------|------|------|
| 機構フィクスチャ | 各手法の文書に列挙した少数レース | 不変条件、方向、閉形式との一致 |
| `dgp-sim` | 既存手法のシミュレータが順位を生成する。訓練 2,400 / 検証 800 / テスト 800 レース。頭数は 8〜14 の一様整数。seed `20261018` | 物理側を生成過程にしたときの提案手法の近似 |
| `dgp-pl` | 提案手法の文書 7.2 の Plackett-Luce 混合が順位を生成する。分割と seed は同じ | 統計側を生成過程にしたときの既存手法の対数損失を記録する |
| 実レース | 日付で前半を訓練、後半を検証・テストに分ける | 任意。無い場合は PoC の合格条件に含めない |

`dgp-sim` の馬属性は提案手法 7.2 と同じ乱数手順で引き、着順だけを既存シミュレータで付ける。`dgp-pl` は同じ属性に、提案手法の生成式で着順を付ける。属性の引き方を揃えることで、差が着順モデル側に残る。

オッズ、人気、上がりタイム、当該レースの着順から作った特徴は、どちらの訓練にも入れない。

## 4. 共通指標

出走頭数 n のレースで、勝者の予測確率を p、定数予測 1/n の対数損失を null とする。

| 指標 | 定義 |
|------|------|
| winner log loss | テストレースについての `-mean(log p_winner)` |
| null log loss | `-mean(log(1/n))`。頭数が 8 固定なら 2.079442 |
| Brier | 馬ごとの `(winProb - 1{win})²` の平均 |
| ECE | 予測勝率を 10 分位に分け、分位内の平均予測と実勝率の絶対差を、頭数で重み付けして平均する |
| top3 較正差 | 予測 `top3Prob` の平均と、実際に 3 着以内だった割合の差 |

対数損失はレース単位で計算し、馬単位の単純平均にしない。

## 5. 対照

| ID | 手続き | 合格 |
|----|--------|------|
| X1 | 共通 JSON を両実装が読む | どちらも検証フィクスチャを拒否しない |
| X2 | `dgp-sim` のテスト 800 レースで提案手法の winner log loss を測る。既存手法は生成器と同一係数で各レース 1,000 回の勝率を出し、その log loss も記録する | 提案手法が null を下回る。既存手法の値は参照値として残す |
| X3 | `dgp-pl` のテスト 800 レースで既存手法の winner log loss を記録する | 記録のみ。既存手法はこの生成過程のパラメータを知らない |
| X4 | 共通 3 指標が両方にあり、着タイムとフレームは既存手法だけが必須 | スキーマが 2 節と一致する |
| X5 | 既存手法は同一 seed で着タイムが一致する。提案手法はサンプリング seed を固定した 1 着頻度が、閉形式の勝率と文書の許容差で一致する | 各手法の再現性項目を満たす |

X2 で既存手法の log loss が小さくなるのは、生成器と予測器が同じ式だからである。この差は「実レースでどちらが当たるか」の判定には使わない。実レースを入れたときだけ、外部のデータで両者を比べる。

## 7. 実装の置き場

| 手法 | PoC の置き場 |
|------|----------------|
| 既存手法 | `packages/sim-core` と Vitest。基本設計のシミュレーション核 |
| 提案手法 | 学習部は Python（`poc/proposed/`）。合格した勝率の式とサンプリングは、のちに TypeScript へ移せる入出力にする |

基本設計は初期段階の実行系を TypeScript に置いている。提案手法の学習に使う LightGBM は、その実行系の外で係数を決め、推論式だけを共有する。
